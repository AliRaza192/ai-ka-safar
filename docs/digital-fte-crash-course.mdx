# Digital FTE Banana: 4-Ghante ka Crash Course

*15 Concepts, 80% Real Use — Skills, System of Record, aur MCP*

Yeh [Mode 2, Manufacturing track](/docs/getting-started#mode-2-the-manufacturing-track) mein doosra course hai. Yeh **saat moves mein se doosra hai**: aap apne pehle se banaye hue agent ko lete ho aur usse pehli baar **AI Worker** ki taraf ek asli kadam uthate ho. Pichla course, [Build AI Agents](/docs/build-agents-crash-course), ne agent khud banaya tha: ek streaming chat agent sessions, guardrails, aur tracing ke saath, sandbox par compute ke liye chal raha tha. Kaam karta tha. Lekin jaise hi aap terminal band karte, sab kuch bhool jata tha, aur uske har tools uski Python mein likhe hue the.

> **Pehle sirf kaam karna dekhna hai?** Neeche [15-minute Quick Win](#the-fifteen-minute-quick-win-succeed-once-then-study-why-it-worked) par jump karo. Aap ek kaam karta hua Skill + Postgres + MCP slice banayenge, phir concepts ke liye wapas aana jo explain karein ke yeh is shape mein kyun hai.

Ek **AI Worker** ek clever agent se zyada hai. Aap ise **AI Employee** ya **Digital FTE** (full-time equivalent) ke naam se bhi sunenge. Yeh teen naam ek hi cheez ke hain, har ek alag angle se describe karta hai: _AI Worker_ batata hai ke yeh kaise banaya gaya hai, _AI Employee_ batata hai ke yeh team mein kahan baithta hai, aur _Digital FTE_ batata hai ke yeh budget mein kaise dikhta hai. Yeh course **AI Worker** (ya sirf **Worker** short mein) use karta hai.

Wohi agent teen tareeqon se evolve hokar AI Worker banta hai. Yeh **extensible hai**: bina rewrite ke naye abilities hasil karta hai. Yeh ek **system of record** ke khilaf chalta hai: company ki ground truth, na ke ek context window jo restart par khaali ho jaye. Aur yeh **owned hai**: aap control karte ho ke yeh kahan chalta hai, kya data rakhta hai, aur kya rules follow karta hai. Ek poora AI Worker hamesha-on, proactive, aur multi-channel bhi hota hai, lekin woh raaste mein baad ke moves hain. Yeh course **foundation** banata hai: extensible, durable, owned core jis par baaki sab cheezein add hoti hain.

Aap wohi SDK aur wohi `SandboxAgent` runtime pichle course se rakhte ho. Ek chalte hue Worker ke do parts hain jo production mein alag deploy hote hain: **harness** (agent ka runtime, SDK loop khud) aur **compute** (**sandbox** jahan agent ka code actually execute hota hai). Jab agent tool chalata hai, woh code apne sandbox ko deta hai; woh sandbox compute hai. Is course mein dono local rehte hain: `UnixLocalSandboxClient` sandbox seedha aapki machine par chalata hai (zero infrastructure, ek API key), aur aap ise Docker, Cloudflare, E2B, ya Modal par ek line change se point kar sakte ho ([Part 5 ka Swap guide](#swap-guide-the-architecture-is-invariant-the-products-are-not)). Harness khud ko always-on cloud service ke tor par deploy karna apna course hai, [Deploy Your Agent Harness to the Cloud](/docs/deploying-agents-crash-course). Aap yahan koi bhi deploy nahi karte. Yeh course woh badalta hai jo runtime ke ird gird hai.

Woh promotion do moves par aati hai, aur un ke beech ka wire, aur neeche ke bullets un teenon mein se ek ek hain. Agent Skills khud discover karta hai; ek wire usse stores se jodta hai.

*   **Capabilities** se **Skills** bante hain: portable folders jo agent demand par discover aur load karta hai, na ke Python mein likhe hue tools.
*   Woh cheezein jo agent restart par kho deta tha woh **Postgres** mein chali jaati hain. Teen mukhtalif cheezein wahan rehti hain, aur woh ek jaisi nahi hain:
    *   **State**: kaam ki mojooda haalat. Kaunsi conversations khuli hain, kya approval ka intezaar kar raha hai.
    *   **System of record**: jo waqai hua uski authoritative, audited trace. Worker ne liya har action, baad mein replay kiya ja sakta hai.
    *   **Memory**: Worker ne kya seekha hai aur jis par woh bharosa kar sakta hai. Pichle cases, reference documents, purani conversations ka khulasa.
*   **MCP (Model Context Protocol)** agent aur un stores ke beech ka **wire** hoga.

Ek aur cheez, aur yeh woh hai jise zyada tar log galat label karte hain. **Semantic recall**, matlab meaning se dhundhna exact match ki bajaye, yeh ek _retrieval method_ hai, na ke chautha store. Aap ise state par, system of record par, ya memory par chala sakte ho. Humein yeh `pgvector` se milta hai, ek extension jo Postgres mein vector search add karta hai. Do sawal dikhate hain ke stores kyun alag hain:

*   _"Hamari company policy is customer case ke liye kya hai?"_ yeh **system of record** se ek authoritative answer maangta hai.
*   _"Kya humne is se pehle aisa sawaal dekha hai?"_ yeh **memory** se poochta hai, aur semantic recall woh tarika hai jis se aap match dhundhte ho.

Wohi database, mukhtalif stores, ek search method jo sab par kaam karta hai.

> **Yaad rakhne wala ek jumla.** Agent ko Worker mein promote karna do moves hai: iski **capabilities** ko iski code se bahar nikalo (Skills), aur iski **state, records, aur memory** ko iski process se bahar nikalo (Postgres, MCP ke zariye reach kiya gaya). Is course mein har cheez un dono moves mein se koi ek hai, ya un ke beech ka wire hai.

### Yeh course Agent Factory thesis mein kahan baithta hai

[Thesis](https://agentfactory.panaversity.org/docs/thesis) saat invariants naam deta hai jo har production agent system satisfy karna chahiye. Pichle course ne **engine** banaya tha (Invariant 4): OpenAI Agents SDK sandbox par. Yeh course **Invariant 5** add karta hai: har Worker ek system of record ke khilaf chalta hai. Engine woh hai jis par Worker _chalta_ hai; system of record woh hai jis ke khilaf woh _chalta_ hai.

Do open standards ise portable rakhte hain. **Skills** (originally Anthropic, ab ecosystem-wide [agentskills.io](https://agentskills.io) par) capabilities ko tools ke beech travel karne dete hain. **MCP** standard wire hai jis se agent record tak pahunchta hai; pichle course mein koi nahi tha, aur yeh yahan key naya pattern hai. Record khud **Neon Postgres + pgvector** hai, chosen kyunki yeh shuru karne ke liye free hai, idle par zero tak scale hota hai, aur ek official MCP server ship karta hai. Product replaceable hai; [Swap guide](#swap-guide-the-architecture-is-invariant-the-products-are-not) alternatives list karta hai.

### 15-concept cheat sheet

Zyada tar production failures teen cheezon mein se kisi ek par trace hoti hain: ek Skill jo agent ne kabhi discover nahi ki, ek database jo waqai source of truth nahi hai, ya ek MCP wire jo data drop karta hai.

15 concepts ek nazar mein (poora map ke liye expand karein)

## The fifteen-minute quick win: succeed once, then study why it worked

Is se pehle ke aap 15 concepts parhein jo explain karein ke _yeh_ architecture kyun kaam karti hai, iska sab se chota version banao jo actually kaam kare. Is section ke khatam hone tak aapke paas hoga:

*   ek Postgres table jo agent ki pehli durable write hold karti hai
*   ek audit row jo record karti hai ke agent ne kya kiya, wohi transaction mein
*   ek MCP boundary jo agent ne cross ki
*   is sawaal ka kaam karta hua jawab: "kya system of record + MCP boundary ne mere liye actually kuch kiya?"

Yeh Part 4 worked example nahi hai; woh poora Worker hai, aath Decisions, sain lines. **Yeh ek screen hai.** Agar aapke paas sirf ek sitting hai, yeh karo, phir concepts ke liye wapas aana jab aap jaanna chahein ke har cheez is shape mein kyun banayi gayi thi.

:::warning Before you start: starter project zip mein hai.

[digital-fte-crash-course.zip](/downloads/digital-fte-crash-course.zip) download karo, unzip karo, `uv sync` run karo, aur `.env` mein `OPENAI_API_KEY` set karo. Ab aapke paas ek fully runnable sandboxed chat agent hai, koi pichla course zaruri nahi. Quick Win phir ek MCP server aur project ke `cli.py` mein \~30 lines add karta hai (plus ek optional Skill folder jo aap Part 4 ke liye rakh sakte ho). Starter unzipped hone ke baad yeh do `uv` commands hai (`uv add`, phir `uv run`).

MCP boundary par focus rakhne ke liye, Quick Win ek standalone `cli.py` chalata hai (ek plain `Agent`, pichle course ka `SandboxAgent` nahi) aur "Remember this: …" ko MCP tool ki docstring ke zariye route karta hai. Yeh koi shell ya filesystem operation nahi chalata, toh isse sandbox client ki zarurat hi nahi.

**Step 1.** Ek Postgres table aur ek choti audit table banao **fresh database ya Neon branch** par, na ke kisi aisi par jis mein pehle se tables hon. (Neon ki web console use karo, ya kisi bhi Postgres par `CREATE DATABASE` jo aap control karte ho; aapko abhi pgvector nahi chahiye.) `notes` aur `audit_log` naam generic enough hain ke existing schema se takra sakte hain, aur neeche ka `CREATE TABLE` khaali target assume karta hai.

```sql
CREATE TABLE notes (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    note_text   TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE audit_log (
    id          BIGSERIAL PRIMARY KEY,
    action      TEXT NOT NULL,
    payload     JSONB NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**Step 2.** Ek 30-line MCP server likho jo ek tool expose karta hai. Poora pattern Concept 14 aur Decision 6 mein dobara aata hai; yeh sab se chota version hai:

```python
# notes_mcp.py
import json
import os
import asyncpg
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("notes")

_pool = None

async def pool():
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(os.environ["DATABASE_URL"])
    return _pool

@mcp.tool()
async def save_note(text: str) -> dict[str, str]:
    """Save a note to the durable notes table. Returns the row_id."""
    p = await pool()
    async with p.acquire() as c:
        async with c.transaction():
            row_id = await c.fetchval(
                "INSERT INTO notes (note_text) VALUES ($1) RETURNING id::text", text)
            await c.execute(
                "INSERT INTO audit_log (action, payload) VALUES ($1, $2::jsonb)",
                "note_saved",
                json.dumps({"row_id": row_id, "len": len(text)}),
            )
    return {"row_id": row_id, "status": "saved"}

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

Audit payload ke liye `json.dumps()` use karo, f-string nahi. Quick Win ki values safe hain (UUID aur int), lekin poora worked example user-typed strings accept karta hai, toh wohi pattern dono ko protect karta hai. `row_id` key important hai: Step 4 ki verification query `payload->>'row_id'` par join karti hai, toh woh exact key payload mein hona chahiye.

**Step 3.** Agent banao. Pehle, SDK, DB driver, aur MCP package install karo (starter pehle se SDK ship karta hai, toh practically aap `asyncpg` aur `mcp` add kar rahe ho):

```bash
uv add openai-agents asyncpg mcp
```

Phir starter ke `cli.py` mein, imports aur `main()` wiring aisi dikhti hai (`cli.py` baqi starter jaisi ship hoti hai rehti hai):

```python
# cli.py — Quick Win shape
import asyncio
import os
from agents import Agent, OpenAIChatCompletionsModel, Runner, set_tracing_disabled
from agents.mcp import MCPServerStdio
from openai import AsyncOpenAI

# Uncomment if your backend is not OpenAI (DeepSeek, OpenRouter, local proxy):
# set_tracing_disabled(True)

async def main():
    # The OpenAI Agents SDK accepts any OpenAI-API-compatible backend.
    # Set OPENAI_BASE_URL only when pointing at a non-OpenAI host.
    client = AsyncOpenAI(
        api_key=os.environ["OPENAI_API_KEY"],
        base_url=os.environ.get("OPENAI_BASE_URL"),
    )
    model = OpenAIChatCompletionsModel(
        model=os.environ["MODEL_NAME"],
        openai_client=client,
    )

    async with MCPServerStdio(
        name="notes",
        params={
            "command": "python",
            "args": ["notes_mcp.py"],
            "env": {**os.environ},  # inherit PATH + DATABASE_URL into the subprocess
        },
        client_session_timeout_seconds=30,  # default 5s is too short for first call to a remote Postgres
    ) as notes:
        agent = Agent(
            name="ChatAgent",
            model=model,
            mcp_servers=[notes],
            instructions="You are a helpful assistant. Use the tools available to you.",
        )
        result = await Runner.run(
            agent,
            "Remember this: the production deploy needs a new env var before Friday.",
        )
        print(result.final_output)

if __name__ == "__main__":
    asyncio.run(main())
```

Teen details naam ke laayak:

*   **`env={**os.environ}`** sab se common Quick Win failure ka fix hai. Agar aap sirf `DATABASE_URL` pass karo, spawned subprocess `PATH` kho deta hai aur `python notes_mcp.py` kuch shells par findable nahi rehta. Parent env inherit karna subprocess ko saaf se shuru karta hai.
*   **`client_session_timeout_seconds=30`** SDK ke 5-second default ko override karta hai. Pehle `save_note` call ko remote Postgres se TLS connection kholna hota hai, fresh pool acquire karna hota hai, aur transaction ke andar do inserts run karne hote hain. 5 seconds par client give up karta hai aur retry karta hai, pehla call server-side commit hota hai, aur aapke paas duplicate rows ho jaate hain.
*   **`set_tracing_disabled(True)`** upar example mein commented hai. Yeh SDK ke `platform.openai.com` ke khilaf trace-upload attempt ko silence karta hai. Real OpenAI run par commented rehne do; uncomment karo agar aapka backend kuch aur hai.

**Step 4.** Run karo.

**Verification, ek SQL query mein:**

```sql
SELECT n.id, n.note_text, n.created_at, al.action, al.payload
FROM notes n
JOIN audit_log al ON al.payload->>'row_id' = n.id::text
ORDER BY n.created_at DESC LIMIT 1;
```

Agar aapko ek row mein apni note text dikhai de aur joined audit row mein `"action": "note_saved"` ke saath matching `row_id`, toh **architecture kaam kar raha hai.** Ek system of record jo truth hold karta hai. Ek MCP boundary jise agent ne cross kiya use likhne ke liye. Ek audit trail jo aap replay kar sakte ho.

Agar ek prompt ke baad `SELECT COUNT(*) FROM notes;` 1 ki bajaye 2 return kare, toh pehle `save_note` call ne client-side timeout kiya aur SDK ne server-side retry kiya. Fix Step 3 mein `client_session_timeout_seconds=30` hai (edit karke dobara run karo). Upar ki verification JOIN ise `LIMIT 1` se chupaati hai, isliye count check karna worth hai.

**Step 5 (optional): Part 4 ke liye Skill seed rakh do.** Upar sab kuch MCP boundary prove karta hai bina Skill ke. Agar aap pehla _move_ baad ke liye staged karna chahte ho, toh abhi ek Skill folder project mein drop karo:

```bash

cat > .claude/skills/log-a-note/SKILL.md << 'EOF'
---
name: log-a-note
description: Saves a short text note to the durable notes table in Postgres, along with a timestamp. Use when the user says "remember this", "save a note", "log that", or otherwise asks for something to be persisted between sessions. Returns the row_id of the saved note.

When this skill activates:

1. Extract the note text from the user's message — everything after "remember:" or "save this:" or similar trigger phrases, or the whole message if no trigger phrase is used.

Folder Part 4 tak ready baitha hai, jahan Claude Code ke andar yehi project chalane se Skill fire hoti hai. Abhi rakhne ka matlab hai ke jab aap pahunchon toh yeh pehle se jagah par hai.

## Part 1: Skills, capability as portable folders

Pichle course ke agent ki capabilities Python mein baked thi. Har tool `tools.py` mein ek `@function_tool`-decorated function tha; har behavior `agents.py` mein ek instruction string tha. Woh ek demo ke liye kaam karta tha. Workforce ke liye kaam nahi karta. **Skills capability ko code se aur folders mein extract karti hain jo agent demand par discover, load, aur execute karta hai**: version-controlled, agents ke beech sharable, bina redeploy ke addable.

### Concept 1: Agent Skill kya hota hai

Ek [Agent Skill](https://agentskills.io/) ek folder hai jis mein ek `SKILL.md` file hoti hai plus optional scripts, references, aur assets. Folder _hi_ skill hai; `SKILL.md` uska entry point hai. Format originally Anthropic ne release kiya tha aur ab ek open standard hai jo [agentskills.io](https://agentskills.io/) par publish hai, Claude Code aur OpenCode aaj do reference clients hain aur uske aage compliant clients ki growing list hai. agentskills.io specification compatibility claims ke liye authoritative source hai.

Minimum viable skill:

```
hello-skill/
└── SKILL.md
```

Contents ke saath:

```yaml
---
name: hello-skill
description: A skill that responds with a friendly greeting tailored to the user's name and the time of day. Use when the user asks to be greeted, says hello, or starts a conversation.
---

# Hello skill

When the user greets you or asks to be greeted:

1. Determine the current local time of day.
2. Compose a friendly, time-appropriate greeting that uses the user's name if available.
3. Keep the greeting under 25 words.

Examples:
- Morning + name known: "Good morning, Sara — hope your week is starting well."
- Evening + no name: "Good evening — happy to be of help."
```

Yeh ek complete, valid skill hai. Shuru hone par client name aur description padhta hai; body sirf tab load hoti hai jab model task ke liye skill select kare. **Koi code. Koi deployment. Koi SDK call. Ek folder markdown file ke saath.**

Woh file-on-disk property hai jo skills ko tools ke beech portable, teams ke beech shareable, aur kisi bhi text artifact ki tarah version-controllable banati hai. Skills woh Python objects nahi hain jo aap import karte ho, API endpoints jo aap call karte ho, ya framework primitives jo aap instantiate karte ho.

### Concept 2: Progressive disclosure, teen-stage skill loading model

Panch skills, sab ek saath loaded, model ko instructions mein daba deti hain jo use abhi nahi chahiye. Isliye skills teen stages mein load hoti hain. Har stage pichle se zyada costly hai, aur agla stage sirf tab load hota hai jab pichla kahe ke skill relevant hai. Woh staged loading **progressive disclosure** hai.

**Stage 1, Discovery.** Startup par, agent har available skill ka `name` aur `description` load karta hai. Spec recommend karta hai ke yeh footprint tiny rakho: roughly **100 tokens per skill**. Panch skills wale Worker ko discovery ke liye roughly 5,000 tokens milte hain, har turn, har conversation. Yeh library mein kya hai yeh jaanne ki cost hai.

**Stage 2, Activation.** Jab model decide karta hai ke kisi task ko skill ki description se match karta hai, woh poori `SKILL.md` body context mein load karta hai. Spec recommend karta hai ke yeh **5,000 tokens se kam** rakho per skill. Zyada tar ache se likhi hui skills 500–2,000 tokens par hoti hain. Activation cost sirf un turns par pay hoti hai jo actually skill use karti hain.

**Stage 3, Execution.** Agar skill ki instructions doosri files refer karti hain (`scripts/` ke neeche script, `references/` ke neeche reference, `assets/` ke neeche template), woh sirf tab load hoti hain jab agent unhe explicitly reach kare. Kuch skills koi references load nahi karti; deep technical skills teen ya char load kar sakti hain.

![Progressive disclosure timeline: startup par, sab skills ke sirf names aur descriptions load hote hain (sasta, har turn par pay hota hai). Activation par, poori SKILL.md body load hoti hai (medium, sirf matching turns par pay hota hai). Execution par, referenced files demand par load hoti hain (variable, sirf jab reach kiya jaye tab pay hota hai).](/img/02-progressive-disclosure-a9a3d68d63ee6a841f5a34447f76d65c.webp)

**Practice mein yeh kaisa dikhta hai, ek chota walkthrough.** Imagine karo aapke customer-support Worker ke paas `.claude/skills/` mein 30 Skills hain, har ek ke saath ek `SKILL.md`. Agent shuru hota hai; runtime har `SKILL.md` padhta hai aur sab 30 files ke liye sirf YAML frontmatter extract karta hai (`name` aur `description`). Roughly 3,000 tokens model ke context mein "available skills" ki table ke tor par utarte hain. Har `SKILL.md` ki body load _nahi_ hoti; `references/` ke neeche ke references load _nahi_ hote; `scripts/` ke neeche ke scripts _padhe bhi nahi jaate_. Model ab jaanta hai ke uske paas kya tools hain, lekin un mein se kisi ko kaise use karna hai nahi.

User message bhejta hai: _"Mujhe ticket TKT-1042 ka haal batao."_ Model apni 30-description list scan karta hai, `summarize-ticket` description match karta hai (jo "ticket ID," "bring me up to speed" mention karti hai), aur decide karta hai ke yeh skill apply hoti hai. _Ab_ runtime poori `summarize-ticket/SKILL.md` body load karta hai, lagbhag 1,500 tokens, context mein. Model operational instructions padhta hai: "ticket ID nikaalo, `lookup_customer` call karo, `find_similar_resolved_tickets` call karo, paanch-section ka summary banao." Woh instructions follow karta hai.

Un instructions ka Step 3 `references/style.md` refer karta hai, summaries ke liye formatting guide. Model us file ke liye reach karta hai; runtime use demand par load karta hai. Baqi 29 skills ki bodies, baqi reference files, `scripts/` ke neeche ke scripts: koi bich kabhi model ke context mein nahi aaya. Sirf sab 30 ka metadata, plus ek skill ki body aur ek reference jo _fire_ hui, ke liye pay kiya gaya. Neeche Predict us gap par numbers rakhta hai.

:::tip PRIMM — Predict

Jawab **(b), roughly 6,900 tokens** hai: 30 × 80 tokens discovery ke liye (2,400), plus ek activate skill ke liye 1,500 tokens, plus ek referenced file ke liye \~2,000 tokens. Cost library size ke saath discovery ke liye linearly scale karti hai, aur per-turn activation aur execution ke liye constant. **Yeh woh hai jo skill library ko affordable banata hai.** Bina progressive disclosure ke, 30 skills × 1,500 tokens body × 4,000 tokens references = 165,000 tokens per turn sirf yeh jaanne ke liye ke agent kya kar sakta hai. Koi yeh nahi chalata.

Skill design ke liye do consequences:

*   **Description key field hai.** Yeh Stage 1 mein fire hoti hai aur determine karti hai ke Stage 2 hota bhi hai ya nahi. Vague description ("helps with PDFs") baar baar fire hoti hai aur activation tokens waste karti hai; sharp description ("extracts text and tables from PDFs, fills PDF forms, merges PDFs; use when working with PDF files") tab fire hoti hai jab hona chahiye aur tab chup rehti hai jab nahi hona chahiye. Zyada tar skill failures description failures hain.

*   **Lambi `SKILL.md` bodies mehengi hain.** `SKILL.md` ko \~500 lines se neeche rakho, ideally 100–300. Depth ko reference files mein move karo. 500-line limit arbitrary nahi hai; yeh woh threshold hai jahan activation cost actual reasoning context ko crowd out karna shuru karti hai.

### Concept 3: SKILL.md likhna, skill ka model se contract

`SKILL.md` file ke do parts hain: **YAML frontmatter** (contract) aur **Markdown body** (operational instructions). Frontmatter agent-facing API hai; body kaam karne wali hai.

**Frontmatter, field by field.**

| Field | Required | Constraint | Purpose |
|-------|----------|------------|---------|
| `name` | Haan | 1–64 chars, lowercase alphanumeric + hyphens, leading/trailing/consecutive hyphens nahi, folder name se match hona chahiye | Skill ka identifier. |
| `description` | Haan | 1–1024 chars, khaali nahi | Trigger surface. Agent discovery par padhta hai ke is skill ko invoke karna hai ya nahi. |
| `license` | Nahi | License name ya bundled license file ka path | Skill kis terms ke under ship hoti hai. |
| `compatibility` | Nahi | ≤500 chars | Environment requirements (intended product, system packages, network access). Zyada tar skills ko zarurat nahi. |
| `metadata` | Nahi | Arbitrary key-value mapping | Client-specific extensions (author, version, etc.). |
| `allowed-tools` | Nahi | Space-separated tool list | Pre-approved tools jo skill use kar sakti hai. Experimental; support varies. |

Minimum viable frontmatter do fields hai:

```yaml
---
name: my-skill
description: One sentence explaining what this skill does and when to use it.
---
```

Ek zyada production-shaped frontmatter:

```yaml
---
name: extract-meeting-notes
description: Extracts structured action items, decisions, and follow-ups from raw meeting transcripts. Use when the user provides a transcript, meeting recording text, or asks to summarize a meeting. Produces a markdown summary with explicit sections for Decisions, Action Items (with owner and deadline), and Follow-ups.
license: MIT
compatibility: Requires Python 3.12+ and access to the OpenAI API.
metadata:
  author: panaversity
  version: "1.2"
---
```

**Description key field hai.** Spec ke good vs. poor examples dobara parho aur farq internalize karo:

> **Good:** "Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction."
>
> **Poor:** "Helps with PDFs."

Good description **kya** batati hai ("extracts text and tables, fills forms, merges"), **kab** ("when working with PDF documents or when the user mentions PDFs, forms, or document extraction"), aur **specific keywords** surface karti hai jo model match kar sake ("PDFs," "forms," "extraction"). Poor wali kuch nahi batati. Description quality yeh determine karne ka sab se bada factor hai ke aapki skill tab fire hoti hai jab hona chahiye aur tab chup rehti hai jab nahi hona chahiye.

**Body, convention se.** Koi format requirements nahi; spec kehta hai "Jo bhi agents ko task effectively perform karne mein madad kare woh likho." Lekin teen sections har ache se likhi hui skill mein nazar aate hain:

1.  **Step-by-step instructions.** Agent kya karta hai, numbered steps mein, operational language mein. Narrative nahi ("Yeh skill refunds mein madad ke liye design ki gayi hai") balki imperative ("Order lookup karo. Policy check karo. Refund issue karo."). Imperative skills narrative se behtar chalti hain.

2.  **Inputs aur outputs ke examples.** Ek ya do chote examples jo input ki expected shape aur output ki expected shape dikhayein. Examples descriptions se lagbhag paanch guna zyada valuable hain model behavior steer karne ke liye. Inhe skip mat karo.

3.  **Common edge cases.** Do ya teen cases jo happy path se obvious nahi hain, typically woh cases jo actually production mein toot chuke hain. Edge cases apni jagah asli failures se hasil karte hain, imagined ones se nahi.

:::tip PRIMM — Predict

Do skills ka `name` field same hai (`summarize-document`) lekin alag folders mein rehti hain: ek `~/.claude/skills/` mein (user-level) aur ek `.claude/skills/` mein (project-level). Current task dono descriptions se match karta hai. Kya hota hai? Teen options: (a) agent randomly ek pick karta hai; (b) project-level skill jeet ti hai folder precedence ki wajah se; (c) agent dono load karta hai aur model ko choose karne deta hai. Confidence 1–5.

:::

Jawab client par depend karta hai, lekin Claude Code aur OpenCode dono mein prevailing convention **(b) hai, project-level user-level par jeet ti hai**. Wohi precedence pattern jo `CLAUDE.md` resolution hai, agentic-coding crash course ki rules-file behavior, aur zyada tar tool configuration ka. Principle: zyada specific context zyada general context ko override karta hai. Ek folder se do skills ke same naam ek alag problem hai; woh usually error hai, kyunki folder names `name` values se match karne chahiye.

### Concept 4: Skill packaging, skills kahan rehti hain aur kaise travel karti hain

Skills filesystem artifacts hain. Yeh woh hai jo unhe portable banata hai; yeh woh hai jis ki wajah se unke packaging conventions matter karte hain. Folder structure sahi rakho aur aapki skill har compliant client mein kaam karti hai; galat rakho aur kisi mein nahi.

**Har tool skills kahan dhundhta hai.**

| Tool | Project-level | User-level (global) |
|------|--------------|---------------------|
| Claude Code | `.claude/skills/<skill-name>/SKILL.md` | `~/.claude/skills/<skill-name>/SKILL.md` |
| OpenCode | `.opencode/skills/<skill-name>/SKILL.md` | `~/.config/opencode/skills/<skill-name>/SKILL.md` |
| OpenCode (fallback) | `.claude/skills/<skill-name>/SKILL.md` | `~/.claude/skills/<skill-name>/SKILL.md` |

**OpenCode fallback portability ke liye key piece hai.** OpenCode pehle apne `.opencode/skills/` se padhta hai, lekin agar skill wahan na mile toh `.claude/skills/` par fallback karta hai. Practical consequence: **apni skill ek baar `.claude/skills/` mein likho, aur yeh bina modification ke dono tools mein kaam karti hai.** Yeh open Agent Skills format ka sab se concrete payoff hai. Wohi `SKILL.md` jo aap Claude Code user ko ship karte ho OpenCode user ke liye kaam karti hai, byte-for-byte.

**Poori folder structure, directory by directory.**

```
my-skill/
├── SKILL.md              # Required: frontmatter + body. Entry point.
├── scripts/              # Optional: executable code jo skill chala sakti hai.
│   ├── extract.py
│   └── normalize.sh
├── references/           # Optional: deep documentation, demand par loaded.
│   ├── REFERENCE.md
│   └── policies/
│       └── us-refund-policy.md
└── assets/               # Optional: templates, schemas, lookup tables.
    ├── report-template.md
    └── status-codes.json
```

Har directory ka ek specific kaam hai:

*   **`scripts/`** executable code rakhta hai jo agent chala sakta hai. Python, Bash, JavaScript: language support client aur sandbox par depend karti hai. Agent scripts ko relative path se invoke karta hai (e.g., `scripts/extract.py`). Scripts self-contained hone chahiye, comment header mein apne dependencies document karein, aur edge cases gracefully handle karein kyunki agent nahi karega.

*   **`references/`** deep documentation rakhta hai jo agent demand par load karta hai. Convention: har reference file ko ek topic par focused rakho (`finance.md`, `legal.md`, `error-codes.md`) taake agent sirf woh load kare jo current task ko chahiye. 5,000-token reference file jo agent session mein ek baar reach kare woh sasta hai; 50,000-token reference file nahi. **References ko SKILL.md se ek level neeche rakho.** `references/category/subcategory/file.md`-style nesting se bacho; spec is par explicit hai.

*   **`assets/`** static resources rakhta hai: document templates, configuration templates, lookup tables, schemas, images. Yeh agent (ya agent ke chalaye hue scripts) dwara _consume_ kiye jaate hain lekin instructions ke tor par _nahi padhe jaate_.

**SKILL.md ke andar file reference syntax.** Skill root se relative paths use karo:

```markdown
For policy details, see [the US refund policy](references/policies/us-refund-policy.md).
To extract the structured data, run `scripts/extract.py`.
The output should follow the template in `assets/report-template.md`.
```

Agent SKILL.md body padhta hai, path dekhta hai, aur referenced file demand par load karta hai. Koi special syntax, koi link resolution gymnastics, sirf relative paths.

### Concept 5: Skills ka composition, choti skills kab chain karein vs ek badi kab likhein

Skills compose hoti hain. Ek "weekly customer-health report" capability ek badi skill ho sakti hai jo research, drafting, formatting, aur review ek shot mein karti hai. Ya char skills ho sakti hain (`research-customer-health`, `draft-customer-health-report`, `format-customer-health-report`, `review-customer-health-report`) jo filesystem ke zariye ek doosre ko hand off karti hain.

Dono kaam karti hain. Unke bohot alag properties hain.

**Ek badi skill.** Discover karna aasan (ek description, ek match). Kam discovery cost (discovery stage mein ek entry). Tighter coupling: jab activation trigger ho, sab steps ek context mein, ek order mein chalte hain. Isolation mein test karna mushkil. Kahin aur reuse karna mushkil. Jab kuch aadhe raaste mein fail ho, model ko abhi tak irrelevant sab pehle ke kaam ke saath recover karna padta hai context mein.

**Bohot choti skills.** Zyada discovery cost (char entries ek ki bajaye). Zyada activation orchestration cost (kuch ko unhe chain karna padta hai). Looser coupling: har step independently test, replace, ya reuse ho sakta hai. Jab ek fail ho, failure localized hai; pehle ke steps ke artifacts disk par hain. **Har step fresh activation paata hai, matlab koi accumulated context pollution nahi.**

![Skills ka composition: monolithic customer-health-report Skill (upar) ek context mein char steps ek activation ke saath chalati hai, vs char choti Skills (neeche) tmp/ files ke zariye hand off karti hain. Monolithic version discover karna simple hai lekin steps ke across context accumulate karti hai; chained version char activations pay karti hai lekin har ek fresh shuru hoti hai, akele reuse ho sakti hai, aur debugging ke liye intermediate artifacts disk par chodti hai.](/img/06-skill-composition-cce735c67dd9ff02077c0d61ea793200.webp)

Jo decision rule practice mein kaam karta hai:

> **Ek skill likho agar steps tightly coupled hain aur rarely akele reuse hoti hain. Bohot skills likho agar koi bhi step kisi alag workflow se akele invoke ho sakti hai, ya agar steps ke beech context-isolation orchestration simplicity se zyada valuable hai.**

Customer support karne wale Worker ke liye, `summarize-ticket` shayad apni skill hai (humans use karti hain, escalation flow use karta hai, weekly digest use karta hai, audit replay use karta hai). `escalate-to-tier-2` shayad apni skill hai (escalation criteria aur tone requirements reuse hoti hain). Decomposition value-of-isolation versus cost-of-orchestration hai; isolation usually do ya teen composed steps ke baad jeet ti hai.

**Filesystem handoff pattern.** Jab skills compose hoti hain, sab se saaf handoff filesystem hai, conversation nahi. Skill A apna output `tmp/research-customer-{id}.md` mein likhti hai. Skill B invoke hoti hai, `tmp/research-customer-{id}.md` se padhti hai, `tmp/draft-customer-{id}.md` mein likhti hai. Skill C draft padhti hai, report likhti hai. Conversation sirf final report dekhti hai; intermediate artifacts disk par rehte hain jahan agent unhe dobara padh sakta hai, insaan inspect kar sakta hai, aur audit trail baad mein dhundh sakta hai. ### Concept 6: Managed Postgres kyun, aur khaas tor par Neon kyun

Thesis systems of record ke baare mein product-agnostic rehti hai: "AI-Native Company ke existing databases, workflows, aur operational platforms (CRMs, ERPs, ticketing systems, data warehouses, ledgers) system of record ke tor par kaam karte hain." Lekin ek scratch se banaye hue agent ke liye, aapko kuch choose karna padta hai. Sawaal "Postgres vs. MongoDB vs. vector DB" nahi hai. Sawaal hai "kaunsa Postgres."

**Postgres kyun, na ke dedicated vector database.** Teen reasons jo 2026 mein bhi hold karte hain.

1.  **Ek database, ek transaction, ek auth boundary.** Vector DB plus relational DB ka matlab do stores consistent rakhne ke liye, do auth systems scope karne ke liye, do backup pipelines maintain karne ke liye. pgvector extension vectors ko un user records, ticket records, aur audit logs ke _bagal mein_ rakhta hai jin se woh related hain: ek JOIN ek JOIN hai, na ke do eventually-consistent services ke beech network hop. Har major managed Postgres provider (AWS RDS, Google Cloud SQL, Azure, Supabase, Neon) by default pgvector ship karta hai, aur yeh consistently [most-installed Postgres extensions](https://neon.com/blog/ten-most-popular-postgres-extensions) mein rank karta hai. Zyada tar workloads ke liye, yeh "kya yeh enough hai" ka empirical jawab hai. Almost hamesha hai.

2.  **Postgres pehle se hard parts karta hai.** Transactions, indexes, foreign keys, row-level security, point-in-time recovery, query planning. Dedicated vector DB ko inhe scratch se invent karna padta hai aur usually kuch mein se kuch worse karta hai. Default boring choice compounding advantages rakhti hai.

3.  **Postgres ke liye har layer par MCP servers hain.** Neon ek ship karta hai (management ke liye). General Postgres MCP servers hain (SQL execution ke liye). Aap apna likh sakte ho (scoped runtime access ke liye). Postgres ke ird gird MCP ecosystem sab se mature hai.

**Neon kyun khaas tor par: teen differentiators.**

*   **Serverless scale-to-zero ke saath.** Free tier idle par kuch cost nahi karta. Worker jo roz 50 conversations handle karta hai apna zyada waqt $0 cost par guzarta hai, na ke provisioned instance ke liye $50/month. Multi-Worker AI-Native Company ki economics ke liye critical jahan bohot Workers bursty hain.

*   **Branching.** Neon database seconds mein branch hota hai: aapke production data ka full copy-on-write clone, query karne ke liye ready. Maqsad dev/test environments aur migration safety hai; agent-relevant use hai **agent ko branch par experiment karne dena bina production ko chhue**. Branch par galat migration branch delete karke revert hoti hai. Non-branchable database par wahi operation backup se restore hai.

*   **First-class MCP integration.** Neon ek [official MCP server](https://neon.com/docs/ai/neon-mcp-server) ship karta hai (remote `https://mcp.neon.tech/mcp` par, OAuth-authed) jo project management, branch lifecycle, SQL execution, aur migration tooling kisi bhi MCP client ko expose karta hai. Hum ise _development_ ke liye use karenge. Critically (aur hum is par wapas aayenge) **Neon explicitly recommend nahi karta ke Neon MCP server production runtime use ke liye ho.** Yeh ek powerful natural-language interface hai; production agents Postgres se narrower, scoped MCP servers ke zariye baat karte hain jo aap khud likhte ho, ya direct connections ke zariye. Farq matter karta hai; Part 3 ise operational banata hai.

(b) Production se branched Neon database mein pehle se saara production data hota hai. (c) Neon database jis par ek ghante se query nahi aayi free tier ke under abhi bhi paisa cost karta hai.

Yeh teen jawab Neon ke SoR ke tor par fit hone ki operational shape hain.

### Concept 7: Worker ka schema, agent ko actually kaunsi tables chahiye

Worker ka system of record sirf "conversations kahin store karo" nahi hai. Yeh ek structured schema hai jo thesis ki cheezein support karta hai jo har Worker karta hai: **truth padho, outcomes likho, traces chodho, similar pehle ka kaam dhundho.** Chhe tables 90% case cover karti hain. Domain specifics ke liye aap aur add karengi; yeh key chhe hain.

```sql
-- 1. CONVERSATIONS: kaam ka top-level unit
CREATE TABLE conversations (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     TEXT NOT NULL,
    started_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ended_at    TIMESTAMPTZ,
    metadata    JSONB NOT NULL DEFAULT '{}'::jsonb,
    -- searchable summary; agent conversation end par populate karta hai
    summary     TEXT
);
CREATE INDEX idx_conversations_user ON conversations(user_id, started_at DESC);

-- 2. MESSAGES: conversation ke turns
CREATE TABLE messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool', 'system')),
    content         TEXT NOT NULL,
    -- token counts aapko cost ke baare mein sochne dete hain bina dobara count kiye
    input_tokens    INT,
    output_tokens   INT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_messages_conv ON messages(conversation_id, created_at);

-- 3. DOCUMENTS: agent ki reference library
CREATE TABLE documents (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source      TEXT NOT NULL,      -- 'policy_library', 'kb_article', 'past_case', etc.
    title       TEXT NOT NULL,
    body        TEXT NOT NULL,
    metadata    JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_documents_source ON documents(source);

-- 4. EMBEDDINGS: documents AUR past conversations ke vector representations
CREATE TABLE embeddings (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    -- in mein se ek populated hai; doosra NULL hai
    document_id     UUID REFERENCES documents(id) ON DELETE CASCADE,
    conversation_id UUID REFERENCES conversations(id) ON DELETE CASCADE,
    chunk_text      TEXT NOT NULL,
    chunk_index     INT NOT NULL,
    embedding       VECTOR(1536) NOT NULL,
    model           TEXT NOT NULL,  -- 'text-embedding-3-small', etc.
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (
        (document_id IS NOT NULL)::int + (conversation_id IS NOT NULL)::int = 1
    )
);
-- semantic search ke liye key index; Concept 8 dekhein
CREATE INDEX idx_embeddings_hnsw
  ON embeddings USING hnsw (embedding vector_cosine_ops);

-- 5. AUDIT_LOG: Worker ka har action, hamesha ke liye replayable
CREATE TABLE audit_log (
    id              BIGSERIAL PRIMARY KEY,
    conversation_id UUID REFERENCES conversations(id) ON DELETE SET NULL,
    actor           TEXT NOT NULL,        -- 'worker:customer-support', 'system', etc.
    action          TEXT NOT NULL,        -- neeche "canonical action vocabulary" dekhein
    target          TEXT,                 -- table name, skill name, etc.
    payload         JSONB NOT NULL,       -- action ka data
    result          JSONB,                -- kya hua
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_audit_conv ON audit_log(conversation_id, created_at);
CREATE INDEX idx_audit_action ON audit_log(action, created_at);

-- 6. CAPABILITY_INVOCATIONS: har skill ya tool call, replay aur metrics ke liye
CREATE TABLE capability_invocations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    capability      TEXT NOT NULL,        -- 'skill:summarize-ticket', 'tool:search_docs', etc.
    arguments       JSONB NOT NULL,
    result          JSONB,
    status          TEXT NOT NULL CHECK (status IN ('ok', 'error', 'timeout')),
    latency_ms      INT,
    cost_cents      INT,                  -- 1/100 cents mein approximate cost
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_cap_conv ON capability_invocations(conversation_id, created_at);
```

Design choices par kuch notes, kyunki har ek matter karti hai:

*   **Ek embeddings table documents aur conversations dono ke liye.** Ek `CHECK` constraint ensure karta hai ke `document_id` ya `conversation_id` mein se exactly ek set ho. Yeh aapko ek query mein "policies AUR past conversations" ke across semantic search karne deta hai; "kya humne is se pehle jawab diya hai?" sawaal ek index paata hai, do nahi.

*   **`audit_log` `BIGSERIAL` use karta hai, `UUID` nahi.** Audit rows constantly likhi jaati hain; simpler integer key inserts ko fast aur ordering ko trivial rakhta hai. Baqi tables `UUID` use karti hain kyunki rows database se bahar jaati hain (API responses mein, URLs mein) aur UUIDs row counts leak karne se bachate hain.

*   **`capability_invocations` skills ko tools se alag karta hai.** Skill invocation aur `@function_tool` invocation conceptually similar hain lekin operationally alag (alag code paths, alag cost profiles, alag failure modes). Unhe ek table mein `capability` discriminator ke saath store karna aapko dono ke saath query karne deta hai jab "agent ne kya kiya?" poochte hue, phir bhi unhe split kar sakta hai jab "skills ka cost vs tools ka kya tha?" poochte hue.

*   **`metadata JSONB` columns escape hatches hain.** Schema har domain-specific field predict nahi kar sakta jo aapko chahiye; JSONB aapko bina migrations ke fields add karne deta hai. Sparingly use karo: jo fields bohot queries mein aate hain unhe columns mein promote karna chahiye.

Yeh **Worker ke liye minimum operational schema** hai: kaam ke liye teen tables (conversations, messages, documents), embeddings ke liye ek, trace ke liye do (audit\_log, capability\_invocations). Domain specifics ke liye aap aur add karengi: ek `customers` table, ek `tickets` table, versioning ke saath ek `policies` table. Wohi shape hain: relational data jo agent MCP ke zariye padhta hai aur likhta hai.

### Concept 8: pgvector basics, types, distance operators, indexes

`embeddings` table woh hai jo Worker ko stored text meaning se search karne deti hai, na ke sirf exact match se. Woh text memory ho sakti hai, system-of-record entry ho sakti hai, ya document ho sakti hai. Search ko power deta hai [pgvector](https://github.com/pgvector/pgvector): ek Postgres extension jo vector data types aur similarity-search operators add karta hai. Yeh har major managed Postgres provider par by default ship hota hai. Zyada tar workloads ke liye, yeh "kya mujhe separate vector DB use karna chahiye?" ka jawab hai. Jawab nahi hai.

**Vector type.** `VECTOR(n)` ek fixed-length floating-point column hai. `n` aapke embeddings ki dimensionality hai: OpenAI ke `text-embedding-3-small` ke liye 1536, `text-embedding-3-large` ke liye 3072, doosre models ke liye varies. **Dimension us model se match hona chahiye jo embedding produce karta hai.** Mix karna sab se common pgvector bug hai: model A se 1536-dim vectors insert karo, model B se 1536-dim vectors ke saath query karo, aur results nonsense hain jabke har query "kaam" karti hai.

2000 se oopar dimensions ke liye, `HALFVEC` type half-precision floats use karta hai (32-bit ki bajaye 16-bit, har value mein kam precision) aur minor recall cost par roughly storage aadha karta hai. Hamare 1536-dim case ke liye, plain `VECTOR(1536)` theek hai.

**Teen distance operators.** pgvector do vectors kitne similar hain yeh measure karne ke teen tarike expose karta hai. Apne use case ke liye ek chuno aur us par raho; mix karna confusion ki recipe hai.

| Operator | Name | Kya measure karta hai | Kab use karein |
|----------|------|----------------------|----------------|
| `<->` | L2 distance (Euclidean) | N-dimensional space mein straight-line distance | Image embeddings, geometric similarity |
| `<#>` | Negative inner product | Dot product (negated) | Jab aapka embedding model _un-normalized_ vectors produce karta hai aur aap magnitude par depend karte ho |
| `<=>` | Cosine distance | Vectors ke beech angle, magnitude se ghair-mutaliq | **Text embeddings: hamare case ke liye default** |

OpenAI ke `text-embedding-3-small` aur `text-embedding-3-large` normalized vectors produce karte hain, jiska matlab cosine distance aur Euclidean distance equivalent rankings dete hain. **Text embeddings ke liye convention se cosine distance (`<=>`) use karo**; yeh sab se common hai, sab se documented hai, aur index ops is ke liye `vector_cosine_ops` naam se hain.

Ek semantic-search query, poora:

```sql
-- Find the 5 documents most similar to the user's question
SELECT d.id, d.title, d.body,
       e.embedding <=> $1 AS distance
FROM embeddings e
JOIN documents d ON d.id = e.document_id
WHERE e.document_id IS NOT NULL  -- conversation embeddings exclude karta hai
ORDER BY e.embedding <=> $1      -- kam distance = zyada similar
LIMIT 5;
```

`$1` yahan user ke sawaal ka embedding hai, query time par generate kiya gaya. `<=>` operator sahi index ke saath is O(n) ko O(log n) banata hai.

**Do index types: HNSW aur IVFFlat.** pgvector ke do practical index choices hain. 2026 tak, recommendation converge ho gayi hai:

*   **HNSW se shuru karo jab tak koi reason na ho.** Graph-based (ek in-memory neighbor graph jo database query time par walk karta hai), slowly build hota hai lekin fast query karta hai, broadest operator support hai, predictable performance. Naye projects ke liye default.
*   **IVFFlat use karo jab build time query time se zyada matter kare.** Partition-based (vectors buckets mein clustered jo baari baari search hote hain), HNSW se 5–6× fast build hota hai, slow query karta hai. Useful jab aap frequently index re-build karo ya insert-heavy workload ho.
*   **DiskANN exist karta hai** (Timescale ke pgvectorscale extension ke zariye, ek separate add-on) bohot bade indexes ke liye jo RAM mein fit nahi hote. Aapko almost certainly zarurat nahi.

Upar schema se HNSW index:

```sql
CREATE INDEX idx_embeddings_hnsw
  ON embeddings USING hnsw (embedding vector_cosine_ops);
```

Do tuning knobs agar tune karo toh: `m` (har node ke connections ki tadad, default 16) aur `ef_construction` (build-time effort, default 64). Defaults zyada tar workloads ke liye sensible hain; sirf tab touch karo jab benchmark kiya ho.

### Concept 9: Embedding pipeline, text andar, queryable vector bahar

Ek embedding text ka ek tukda space mein ek point mein badalta hai. Refunds ke baare ka text doosre refunds ke text ke qareeb utarta hai; login bugs ke baare ka text kahin aur. Toh "similar tickets dhundhna" "qareebatay points dhundhna" ban jata hai. Yeh poora idea hai. Baqi plumbing hai.

Plumbing chaar steps hai, aur har ek mein ek decision matter karti hai:

1.  **Chunk** karo document ko chote tukdon mein jo har ek ek idea carry karein.
2.  **Embed** karo har tukde ko model ko call karke; aapko uska point wapas milta hai.
3.  **Store** karo text, uska point, aur thora sa metadata `embeddings` table mein.
4.  **Query** karo user ke sawaal ko bhi ek point mein badal kar, phir qareebatay stored points dhundh kar.

![Embedding pipeline: raw policy document (upar-bayan) semantic boundaries par \~400-token tukdon mein chunk hoti hai overlap ke saath; har chunk OpenAI ke text-embedding-3-small ke zariye 1536-dim vector mein batch-embed hota hai; vectors VECTOR(1536) rows ke tor par embeddings table mein HNSW index ke saath store hote hain. Query time par (neeche), user ka sawaal wohi embed step se guzarta hai, phir ek SQL query cosine-distance operator ke saath top-5 qareebatay chunks dhundhti hai. Neeche teen traps call out kiye gaye hain: model mismatch, galat chunk size, bina filter ke sources mix karna.](/img/07-embedding-pipeline-15dd75de40f51eb7176d39b36131c7c8.webp)

**Chunking.** Embedding models ke token limits hain: OpenAI ke `text-embedding-3-small` har chunk ke liye 8,191 tokens accept karta hai, bohot zyada jo aap usually chahte ho. Sawaal "maximum kya hai" nahi balki "chunk size kya hai jo meaning ka woh unit preserve kare jo user dhundhega." Teen rules jo practice mein kaam karte hain:

*   **Semantic boundaries par chunk karo jab kar sako.** Section headings, paragraph breaks, source mein structural markers. Jo chunk sentence ke beech mein khatam ho woh badly retrieve karta hai.
*   **Zyada text ke liye 200–500 tokens per chunk target karo.** Meaning carry karne ke liye enough lamba, specific hone ke liye enough chota. Longer chunks wale documents "sab se weak match" karte hain na ke "sahi cheez se strong match."
*   **Chunks ke beech 10–20% overlap rakho** jo natural boundaries par girte hain. Overflow storage cost karta hai lekin recall improve karta hai jab user ka sawaal chunk boundary ke qareeb ho.
*   **Jo pehle se chota hai use chunk mat karo.** Jo documents \~300 tokens se neeche hain (single resolved tickets, choti policy paragraphs, FAQ entries) ko chunking ki zarurat nahi; unhe ek tukde ke tor par embed karo. Neeche ka chunker lambi source documents (policy PDFs, knowledge-base articles, conversation transcripts) ke liye shaped hai. Worked example ke seed corpus of short resolved tickets ke liye, aap chunker skip kar sakte ho aur har ticket ko single chunk ke tor par embed kar sakte ho (Decision 5 har ticket ko ek `documents` row ke tor par store karta hai jiska `body` `summary || '\n' || resolution` hai, aur use embed karta hai).

Worked example ke liye ek typed chunking function:

```python
# src/chat_agent/embedding/chunker.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Chunk:
    text: str
    index: int
    source_offset: int  # original document mein character offset

def chunk_text(
    text: str,
    target_tokens: int = 400,
    overlap_tokens: int = 60,
) -> list[Chunk]:
    """Split text into overlapping chunks at paragraph boundaries.

    Approximates tokens as words * 0.75 — fine for chunking; not for
    actual token counting. Use tiktoken for precise counts.
    """
    paragraphs: list[str] = [p.strip() for p in text.split("\n\n") if p.strip()]
    target_words: int = int(target_tokens / 0.75)
    overlap_words: int = int(overlap_tokens / 0.75)

    chunks: list[Chunk] = []
    current: list[str] = []
    current_word_count: int = 0
    source_offset: int = 0

    for para in paragraphs:
        para_words: int = len(para.split())

        if current_word_count + para_words > target_words and current:
            chunks.append(Chunk(
                text="\n\n".join(current),
                index=len(chunks),
                source_offset=source_offset,
            ))
            # carry overlap forward
            overlap_chunk: list[str] = []
            overlap_count: int = 0
            for prev in reversed(current):
                if overlap_count + len(prev.split()) > overlap_words:
                    break
                overlap_chunk.insert(0, prev)
                overlap_count += len(prev.split())
            current = overlap_chunk
            current_word_count = overlap_count
            source_offset += sum(len(p) for p in current) + 2 * len(current)

        current.append(para)
        current_word_count += para_words

    if current:
        chunks.append(Chunk(
            text="\n\n".join(current),
            index=len(chunks),
            source_offset=source_offset,
        ))

    return chunks
```

**Embedding.** Batched chunks ke saath model call karo (OpenAI API ek request mein inputs ki arrays accept karta hai, har chunk ke liye ek call se bohot zyada efficient):

```python
# src/chat_agent/embedding/embedder.py
from openai import AsyncOpenAI

EMBEDDING_MODEL: str = "text-embedding-3-small"
EMBEDDING_DIM: int = 1536  # table column match hona chahiye

async def embed_chunks(
    client: AsyncOpenAI, chunks: list[str],
) -> list[list[float]]:
    """Embed a batch of chunks. Returns one vector per chunk, in order."""
    response = await client.embeddings.create(
        model=EMBEDDING_MODEL, input=chunks,
    )
    return [item.embedding for item in response.data]
```

:::warning pgvector ko asyncpg se register karo, warna INSERTs silently fail hongi

`embed_chunks` jo vectors return karta hai woh Python `list[float]` hain. Out of the box, `asyncpg` nahi jaanta ke pgvector ka `VECTOR(1536)` column unhe vector literal ke tor par serialize chahta hai, toh woh unhe Postgres `real[]` array ke tor par bhejta hai aur INSERT ya toh error deta hai `expected vector, got list[float]` ya (bura) silently kuch store karta hai jo query time par fail hota hai. **Connection par ek baar type register karo** embeddings likhne se pehle:

```python
from pgvector.asyncpg import register_vector

await register_vector(conn)

# Option B (production ke liye recommended): pool init callback taake har
# pooled connection automatically register ho, bhoolne ka chance na ho.
pool = await asyncpg.create_pool(
    NEON_DATABASE_URL, init=register_vector,
)
```

Aapko sirf un connections par zarurat hai jo `embedding` column padhte ya likhte hain. Decision 5 neeche pool form use karta hai; Decision 6 ka MCP server wohi pattern use karta hai.

**Agar aapka inference provider OpenAI nahi hai toh?** OpenAI ek hi major provider hai jo first-class embeddings API bhi ship karta hai. Agar aap inference DeepSeek, Anthropic, Gemini, ya local model ke zariye route karte ho, toh aapke paas char options hain. Ek chuno `VECTOR(n)` column banane se pehle: column dimension embedding model se match hona chahiye.

| Model | Dimensions | Cost (input, per 1M tokens) | Kahan hai | Kab use karein |
|-------|-----------|----------------------------|-----------|----------------|
| `text-embedding-3-small` | 1536 | $0.02 | OpenAI (aur OpenAI-compatible aggregators jaise OpenRouter) | **Default agar aapke paas OpenAI key hai.** Sasta, fast, zyada tar retrieval ke liye acha. |
| `text-embedding-3-large` | 3072 | $0.13 (standard) / $0.065 (batch) | OpenAI | Jab aapne `-small` ko underperform karte hue measure kiya ho. |

Headline cost number: 50,000 chunks ko \~300 tokens each par embed karna = 15M tokens × $0.02/M = **$0.30** OpenAI par. Wohi `-large` ke saath $1.95 hai. Local 384-dim model ke saath, $0 plus 30 seconds CPU. Embeddings bill par sab se sasti line hai; choice rarely dollar dial move karti hai, lekin architecture zarur move karti hai.

**Dimension contract hai.** `VECTOR(1536)` sirf 1536-dim vectors accept karta hai. Agar aap `text-embedding-3-small` (1536) se `all-MiniLM-L6-v2` (384) par switch karo, toh column ko `VECTOR(384)` ke tor par re-create karo aur har row re-embed karo. pgvector ke saath koi "close enough fits" nahi hai; dimensions absolute hain.

**Re-embedding.** Kab re-embed karo? Teen triggers:

1.  **Source document badal gayi.** Un saari embeddings ko delete aur dobara insert karo jinka `document_id` match karta hai.
2.  **Embedding model badal gaya.** Lifetime ki migration; agar aap `-small` se `-large` par switch karo, har existing embedding nayi ke saath incompatible hai. Sab kuch re-embed karo, ya transition ke doosre daur mein do embedding columns chalao.
3.  **Chunking strategy badal gayi.** Agar aap decide karo ke 400 tokens galat tha aur 250 sahi hai, toh re-chunk aur re-embed karo. Apne chunks ko version karna (`metadata` JSONB mein `chunk_strategy_version` store karna) aapko yeh safely karne deta hai.

Jawab: **lagbhag certainly woh nahi jo aap chahte the**. Bina unhe distinguish kiye documents aur messages ko retrieval results mein mix karna incoherent answers produce karta hai: model top result dekhta hai jo customer ki pehli message hai aur use authoritative documentation ke tor par treat karta hai. Sahi pattern hai query mein **source type ke saath filter karna**: ya join karke `WHERE document_id IS NOT NULL` se document search ke liye filter karna, ya do alag searches chala kar unhe alag weights ke saath rank karna. Schema ka `CHECK` constraint jo ensure karta hai ke `document_id`/`conversation_id` mein se exactly ek set ho yeh filter ko sasta aur intent ko explicit banata hai.

**Poor retrieval debug karna.** Jab top-k results expectations se match na kare, chaar checks order mein, har ek ek common cause rule out karta hai:

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| Sab top-5 distances > 0.7 hain (cosine distance, toh > 0.5 "door" hai) | Query embedding model corpus embedding model se alag hai | Confirm karo dono ne wohi `EMBEDDING_MODEL` se gaye. `text-embedding-3-small` ko `-large` ke saath, ya local ko OpenAI ke saath mix karna dono pools mein nonsense ranks produce karta hai. |
| Top-5 results sab ek source type se hain jab variety expect ki | Source-type filter missing hai | Query mein `WHERE document_id IS NOT NULL` (ya `CHECK` constraint ka sahi side) add karo, ya do ranked queries chala kar explicit weights ke saath merge karo. |
| Top-k lagbhag identical queries ke beech wildly change hota hai | Chunk size bohot chota hai (har chunk mein enough context nahi) | Bade chunks ke saath re-chunk karo (200, phir 400, phir 600 tokens) aur re-embed karo. Wohi query dobara chalan se ab stable top-k milna chahiye. |
| Query kuch return nahi karti | HNSW index missing hai, ya vector dimension mismatch hai | psql mein `\d+ embeddings` confirm karo ke column `VECTOR(1536)` hai aur HNSW index `vector_cosine_ops` ke saath exist karta hai. Agar column galat dimensionality hai, toh re-create karo. |

Teen diagnostic queries jo `scratch.sql` mein rakhne ke laayak hain:

```sql
-- 1. Distance band on the top-5 for a known-good query
SELECT chunk_text, embedding <=> :query_vec AS distance
FROM embeddings ORDER BY distance LIMIT 5;

-- 2. Source-type breakdown of top-20 (catch the "wrong source dominates" bug)
SELECT
  CASE WHEN document_id IS NOT NULL THEN 'document' ELSE 'message' END AS src,
  COUNT(*)
FROM (SELECT * FROM embeddings ORDER BY embedding <=> :query_vec LIMIT 20) t
GROUP BY src;

-- 3. Confirm the index is actually being used
EXPLAIN (FORMAT TEXT) SELECT id FROM embeddings ORDER BY embedding <=> :query_vec LIMIT 10;
```

### Concept 10: Audit trail as discipline, Worker ke liye "reads aur writes" ka matlab

Agent ka har meaningful action database mein ek row chodna chahiye. Us row ke bina, aap baad mein jawab nahi de sakte "agent ne kya kiya, aur kab?" Woh trail woh hai jo real action ko plausible-sounding reply se alag karta hai.

Operational terms mein translate karein: **agent ka har meaningful action `audit_log` mein ek row likhta hai, plus ek zyada structured row `capability_invocations` mein agar yeh skill ya tool call hai.** Data jis par action ho raha hai uski appropriate table mein rehta hai (message `messages` mein jaata hai, document update `documents` mein jaata hai); _us action ke hone ka fact_ `audit_log` mein rehta hai. Dono foreign key se jude hue hain.

**Kya log karein.**

*   Har model call: input tokens, output tokens, model name, cost estimate
*   Har skill invocation: skill name, arguments, result summary, latency, success/error/timeout
*   Har database write: kaunsi table, kya badla (JSONB payload), kaunsi conversation context ke under
*   Har external tool call: tool name, input, output summary, latency
*   Har guardrail event: kaunsa guardrail trip hua, input kya tha, action kya tha (blocked/allowed/modified)

**Kya log na karein.**

*   Har turn par poori conversation history; woh pehle se `messages` mein hai, aap use dobara store kar rahe ho
*   Sensitive payload data verbatim agar row humans ke liye queryable hai; hash ya summary store karo, poora data restricted table mein rakho
*   Internal model reasoning jo user ko nahi dekhni chahiye; yeh ek context-management decision hai, audit decision nahi

**Replay test.** Ek acha audit trail ek specific test pass karta hai: **ek conversation\_id aur timestamp diye hue, aap bina model dobara chalaye agent ne kya kiya aur kyun reconstruct kar sakte ho.** Agar aapka audit log yeh test pass nahi karta, toh yeh logging hai, auditing nahi.

Ek concrete write-on-action helper, har jagah use hota hai jab capability chalti hai:

```python
# src/chat_agent/audit.py
import time
import json
from typing import Any
from uuid import UUID
import asyncpg

async def log_capability(
    pool: asyncpg.Pool,
    conversation_id: UUID,
    capability: str,
    arguments: dict[str, Any],
    result: Any,
    status: str,
    started_at: float,
    cost_cents: int | None = None,
) -> None:
    """Write a capability_invocations row plus a denormalized audit_log row.

    Both writes happen in one transaction so they're either both present
    or both absent — the audit trail never gets partial.
    """
    latency_ms: int = int((time.monotonic() - started_at) * 1000)

    async with pool.acquire() as conn:
        async with conn.transaction():
            await conn.execute(
                """INSERT INTO capability_invocations
                   (conversation_id, capability, arguments, result, status,
                    latency_ms, cost_cents)
                   VALUES ($1, $2, $3::jsonb, $4::jsonb, $5, $6, $7)""",
                conversation_id, capability,
                json.dumps(arguments), json.dumps(result),
                status, latency_ms, cost_cents,
            )
            await conn.execute(
                """INSERT INTO audit_log
                   (conversation_id, actor, action, target, payload, result)
                   VALUES ($1, $2, $3, $4, $5::jsonb, $6::jsonb)""",
                conversation_id, "worker:customer-support",
                "capability_invoked", capability,
                json.dumps({"arguments": arguments, "latency_ms": latency_ms}),
                json.dumps({"status": status, "result": result}),
            )
```

Ek transaction mein do writes key detail hai. **Aadhe likhe hue audit trails missing audit trails se bura hain**: woh completeness suggest karte hain bina deliver kiye. Ya toh dono rows jaati hain ya koi nahi.

**Canonical action vocabulary.** `audit_log` mein likne wali har site ek choti, agreed list se `action` value choose karti hai. Yahan drift (codebase mein wohi event teen alag naam se jaana) woh hai jo replay queries ko chhe mahine baad fragile banata hai. Worked example mein chhe values, aur kaunsa code path har ek likhta hai:

| `action` | `target` | Kahan likha gaya |
|----------|----------|------------------|
| `message_received` | (null) | `cli.py`, jab user message bhejta hai aur `messages` mein row utarti hai |
| `message_sent` | (null) | `cli.py`, jab agent ka jawab `messages` mein utarta hai |
| `skill_activated` | skill name | `cli.py`, skill load ke liye `RunItemStreamEvent` par |
| `capability_invoked` | capability id | `log_capability` helper upar, har skill ya MCP-tool call par |
| `mcp_called` | tool name | `cli.py`, har MCP tool return hone ke baad (`capability_invoked` se lower-level; ek ya doosra consistently use karo) |
| `refund_issued` / `refund_blocked` | order id | `customer-data` MCP server ka `issue_refund` tool, success aur policy denial par |

`capability_invoked` aur `mcp_called` mein se ek chuno aur us par raho; dono per call likhna double-count karta hai. Worked example agent-side helper ke liye `capability_invoked` use karta hai (Decision 7) aur MCP tools ke andar state-changing writes ke liye named domain actions jaise `refund_issued` (Decision 6). Domain-state writes hamesha apna action naam paate hain taake audit row business event ke liye receipt ho, sirf us tool call ke liye nahi jo trigger kiya.

**Yeh sirf logging kyun nahi hai.** Teen properties audit data ko log data se alag karte hain:

1.  **Replayable.** Schema aapko `audit_log` se `messages` se `capability_invocations` ke saath join karke agent ka reasoning trace reconstruct karne deti hai. JSONL file mein ek log line yeh nahi karta.
2.  **Queryable.** "Agent ne pichle mahine customer X ko kya bataya, aur kis policy ko cite kiya?" ek SQL query hai. "Pichle 7 dinon mein kis skill ne sab se zyada timeouts trigger kiye?" ek SQL query hai. Logs ke liye grep aur luck chahiye.
3.  **Trustworthy.** Audit rows business data ke saath same database mein hain. Woh saath mein backup hote hain, saath mein point-in-time-recoverable hain, saath mein access-controlled hain. Woh agent process, deployment region, aur model version se survive karte hain.

Yeh woh hai jo thesis kahti hai jab kehti hai "Workers sirf tab governable hote hain jab ek ledger unhe legible banaye, capability, cost, latency, aur outcome ki units ke tor par." Aapki `audit_log` aur `capability_invocations` tables _hi_ woh ledger hain. Unhe waisa treat karo.

## Part 3: MCP, agent ko system of record se wire karna

Part 1 ne agent ko Skills ki library di. Part 2 ne use Postgres system of record diya. **Part 3 dono ko Model Context Protocol ke saath wire karta hai**: open standard jo batata hai ke agents external state aur external capability ko kaise reach karte hain. Thesis MCP ki jagah ke baare mein direct hai: _"MCP woh hai jis se workforce [apne systems of record] tak pahunchta hai: har authoritative store MCP server ke zariye kisi bhi Worker ke liye addressable ban jaata hai, policy ke under."_ Yeh Part use operational banata hai.

### Concept 11: MCP kya hai aur kya nahi hai

**Model Context Protocol** ([modelcontextprotocol.io](https://modelcontextprotocol.io/)) ek open client/server protocol hai (originally Anthropic se, ab open standard ke tor par governed) jo batata hai ke AI agent external tools, data, aur prompts se kaise connect hota hai. Framing jo repeat hoti hai woh "USB-C for AI tools" hai: ek protocol, bohot implementations, kisi bhi side ko swap karo bina doosri ko tode. Framing sahi hai; saari metaphors ki tarah, iski limits bhi hain jo naam ke laayak hain.

**MCP kya hai.** Ek protocol. Ek specification. Teen primitives jo server client ko expose kar sakta hai.

1.  **Tools**: functions jo model invoke kar sakta hai. Client unhe list karta hai, model ek choose karta hai, server use execute karta hai. Conceptually pichle course ke `@function_tool` decorator jaisa, lekin implementation MCP server process mein rehta hai, agent ki process mein nahi. Yeh ab tak sab se zyada used primitive hai.
2.  **Resources**: read-only data jo agent fetch kar sakta hai. Files, database query results, API responses. Inhe MCP ka GET-only side samjho. Practice mein tools se kam common, lekin "agent ko yeh document demand par padhne do" ke liye useful.
3.  **Prompts**: reusable prompt templates jo server provide karta hai. Ek team standardized prompts publish kar sakta hai (e.g., "customer-support triage prompt," "bug-report template"). Agents unhe by name request karte hain. Practice mein sab se kam used primitive, lekin jab standardised workflows matter karein tab valuable.

**MCP kya nahi hai.** Yeh framework nahi hai (aap iske _upar_ agent nahi banate, aap ise apne agent ke _saath_ wire karte ho). Yeh service nahi hai (koi hosted endpoint nahi hai jo aapko "MCP" deta hai — aap servers khud chalate ho ya existing ones use karte ho). Yeh agent ka replacement nahi hai (MCP ke paas koi planning, reasoning, ya memory nahi hai; yeh sirf tools, data, aur prompts expose karta hai). Yeh auth system nahi hai (authentication transport layer par hoti hai, protocol khud mein nahi — iska matlab aapko alag se auth manage karni padti hai).

**MCP ka transport layer.** MCP do transports support karta hai:

*   **stdio**: client ek subprocess spawn karta hai, MCP messages stdin/stdout ke zariye pass hote hain. Yeh Quick Win aur Part 4 mein use hota hai. Simple hai, lekin sirf local servers ke liye kaam karta hai.
*   **Streamable HTTP**: client HTTP ke zariye server se baat karta hai, optional Server-Sent Events (SSE) streaming ke saath. Remote servers ke liye; Neon ka MCP server yeh use karta hai.

Dono transports same protocol speak karte hain; farq sirf hai ke bytes kaise travel karti hain. Ek MCP server ko stdio par expose karo aur woh local kaam karta hai; usse HTTP par expose karo aur woh remote kaam karta hai. Client-side code same rehta hai.

### Concept 12: Neon MCP server

Neon ek [official MCP server](https://neon.com/docs/ai/neon-mcp-server) ship karta hai jo aapke Neon project ko kisi bhi MCP-compatible client se manage karne deta hai. Yeh remote hai (`https://mcp.neon.tech/mcp` par), OAuth-authed, aur project management, branch lifecycle, SQL execution, aur migration tooling expose karta hai.

**Yeh kya karta hai.** Neon MCP server aapko natural language mein Neon projects manage karne deta hai: databases create karna, branches banana, SQL queries chalana, migrations run karna. Claude Code ya OpenCode mein aap bolo "mere liye ek nayi branch banao" aur woh MCP ke zariye kar deta hai.

**Yeh kya nahi karna chahiye.** Neon khud explicitly kehta hai: **Neon MCP server production runtime use ke liye nahi hai.** Yeh development aur testing ke liye ek powerful natural-language interface hai. Production agents ko Postgres se baat karne ke liye narrower, scoped MCP servers chahiye jo aap khud likhte ho (Concept 14), ya direct connections. Kyun? Kyunki Neon MCP server poore Neon project par full access deta hai — branches create karna, SQL chalana, migrations — woh sab cheezein jo ek production agent ko kabhi nahi karni chahiye.

**Development vs runtime: ek important farq.** Development mein, Neon MCP server aapka best friend hai: "ek branch banao, schema apply karo, test data insert karo, query chalao." Runtime mein, yeh ek loaded gun hai: agar agent galti se `DROP TABLE` chala de kyunki model ne galat interpret kiya, toh production data gayab. Isliye Part 4 ke worked example mein do alag MCP servers hain: ek development ke liye (Neon ka), ek runtime ke liye (aapka custom `customer-data` MCP server jo sirf safe operations expose karta hai).

**Authentication.** Neon MCP server OAuth use karta hai. Jab pehli baar connect karo, aapko browser mein Neon login karna padta hai; token phir cache hota hai. Production ke liye, aap apne custom MCP server mein direct `DATABASE_URL` use karte ho (jaise Quick Win mein kiya).

### Concept 13: MCP ko Agents SDK se connect karna

OpenAI Agents SDK ke paas MCP ke liye built-in support hai. Aap MCP servers register karte ho jab agent banate ho, aur model automatically un servers ke tools dekhta hai apne available tools ke tor par. Yeh woh wiring hai jo Quick Win mein `MCPServerStdio` ke zariye dikhai thi.

**SDK integration kaise kaam karti hai.** Jab aap `Agent(mcp_servers=[...])` pass karte ho, SDK startup par har MCP server se connect hota hai aur `list_tools()` call karta hai. Server jo tools expose karta hai woh model ke liye available tools mein add ho jaate hain, bilkul waise jaise `@function_tool`-decorated functions. Model ko pata nahi ke tool MCP server par hai ya agent ki process mein — dono same dikhte hain.

```python

from agents.mcp import MCPServerStdio

async with MCPServerStdio(
    name="notes",
    params={
        "command": "python",
        "args": ["notes_mcp.py"],
        "env": {**os.environ},
    },
    client_session_timeout_seconds=30,
) as notes_server:
    agent = Agent(
        name="ChatAgent",
        model=model,
        mcp_servers=[notes_server],
        instructions="You are a helpful assistant.",
    )
    result = await Runner.run(agent, "Remember this: meeting at 3pm.")
```

**Trust boundary.** MCP server ek trust boundary hai. Agent MCP server ko tool call bhejta hai; server decide karta hai ke kya karna hai. Agent directly database access nahi karta — woh MCP server ke zariye request karta hai. Yeh woh boundary hai jo production mein matter karti hai: agent ko sirf woh karna chahiye jo MCP server allow karta hai.

**Model kya dekhta hai.** Jab SDK `list_tools()` call karta hai, har MCP tool ka naam, description, aur input schema wapas aata hai. Model wohi information dekhta hai jab decide karta hai ke kaunsa tool call karna hai. Isliye MCP tool ki docstring itni important hai — yeh woh description hai jo model padhta hai (Quick Win mein, docstring ne saara routing kiya).

**Timeout aur error handling.** MCP server ke saath baat karte waqt do common issues hain:

1.  **Timeout**: pehla call remote Postgres ke liye TLS connection, pool acquisition, aur transaction ke zariye jaata hai. Default 5-second timeout bohot chota hai. `client_session_timeout_seconds=30` fix hai.
2.  **Server crash**: agar MCP server process crash ho jaaye, SDK gracefully handle karta hai aur model ko batata hai ke tool unavailable hai. Model phir decide karta hai ke kya karna hai (usually apologize karta hai aur batata hai ke service temporarily down hai).

Kya `notes` server ko pata chalta hai is call ke baare mein? Jawab: **Nahi.** MCP servers ek doosre se independent hain. SDK sirf us server ko call route karta hai jis ka tool model ne select kiya.

### Concept 14: Custom MCP servers, kab apna server likhein vs `@function_tool` kab use karein

Zyada tar cases mein, aapko custom MCP server likhne ki zarurat nahi — `@function_tool` sufficient hai. Lekin kuch situations mein MCP server likhna sahi choice hai. Decision tree yeh hai:

**`@function_tool` use karo jab:**

*   Tool agent ki process mein chal sakta hai bina external state ko chhueye.
*   Tool ko sirf ek specific agent chahiye, na ke kayi agents ya tools ke beech share karna.
*   Tool ka logic simple hai aur bina database ke kaam karta hai.

**Custom MCP server likho jab:**

*   Tool ko database ya external service access chahiye jo agent ki process ke bahar hai.
*   Tool ko multiple agents ya clients ke beech share karna hai.
*   Tool ek trust boundary chahiye — agent ko direct database access dena unsafe hai.
*   Tool ko apna connection pool, auth, aur lifecycle manage karna hai.

**Ek custom MCP server ka anatomy.** Quick Win ka `notes_mcp.py` sab se chota example tha. Ek production-shaped custom MCP server thoda zyada structured hota hai:

```python
# customer_data_mcp.py
import json
import os
import asyncpg
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("customer-data")

_pool = None

async def get_pool():
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(os.environ["DATABASE_URL"])
    return _pool

@mcp.tool()
async def lookup_customer(customer_id: str) -> dict:
    """Look up a customer record by ID. Returns name, email, account status."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        row = await conn.fetchrow(
            "SELECT id, name, email, account_status FROM customers WHERE id = $1",
            customer_id,
        )
        if row is None:
            return {"error": "Customer not found"}
        return dict(row)

@mcp.tool()
async def get_customer_tickets(customer_id: str, limit: int = 10) -> list[dict]:
    """Get recent support tickets for a customer."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        rows = await conn.fetch(
            """SELECT id, subject, status, created_at
               FROM tickets WHERE customer_id = $1
               ORDER BY created_at DESC LIMIT $2""",
            customer_id, limit,
        )
        return [dict(r) for r in rows]

@mcp.tool()
async def issue_refund(order_id: str, amount_cents: int, reason: str) -> dict:
    """Issue a refund for an order. Requires amount in cents and a reason."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        async with conn.transaction():
            # Verify order exists and is refundable
            order = await conn.fetchrow(
                "SELECT id, total_cents, status FROM orders WHERE id = $1", order_id
            )
            if order is None:
                return {"error": "Order not found"}
            if order["status"] != "completed":
                return {"error": "Only completed orders can be refunded"}
            if amount_cents > order["total_cents"]:
                return {"error": "Refund exceeds order total"}

            # Issue refund
            refund_id = await conn.fetchval(
                """INSERT INTO refunds (order_id, amount_cents, reason, status)
                   VALUES ($1, $2, $3, 'pending') RETURNING id""",
                order_id, amount_cents, reason,
            )

            # Audit trail
            await conn.execute(
                """INSERT INTO audit_log (actor, action, target, payload)
                   VALUES ($1, $2, $3, $4::jsonb)""",
                "worker:customer-support", "refund_issued", order_id,
                json.dumps({"refund_id": str(refund_id), "amount_cents": amount_cents}),
            )

            return {"refund_id": str(refund_id), "status": "pending"}

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

Is server ke baare mein teen important cheezein:

1.  **Scoped access.** Sirf specific operations expose kiye gaye hain (`lookup_customer`, `get_customer_tickets`, `issue_refund`). Agent `DROP TABLE` nahi chala sakta, `DELETE FROM customers` nahi chala sakta, schema nahi badal sakta. Yeh trust boundary hai.
2.  **Business logic server mein hai.** Refund validation (order exists? completed? amount valid?) server mein hai, agent ke prompt mein nahi. Agar model galat arguments bheje, server reject karega.
3.  **Audit trail built-in hai.** `issue_refund` ek hi transaction mein refund aur audit row likhta hai. Half-written audit trails impossible hain.

**stdio vs HTTP transport.** Part 4 stdio use karta hai (local development ke liye simple). Production ke liye, aap HTTP transport par switch kar sakte ho taake MCP server alag process ya machine par ho:

```python
# Local development: stdio
mcp.run(transport="stdio")

# Production: HTTP
mcp.run(transport="http", host="0.0.0.0", port=8080)
```

:::note Quick check

Aap ek MCP server likh rahe ho jo customer data expose karta hai. Model ko sirf read access chahiye, lekin aap `issue_refund` bhi expose karna chahte ho (write operation). Kya yeh safe hai ek hi server mein dono rakhna? Jawab: **Haan**, jab tak write operation server-side validation ke saath aaye. Trust boundary server hai, na ke transport. Agent sirf woh kar sakta hai jo tools allow karte hain; server har call par validate karta hai.

### Concept 15: MCP load ke neeche, transport choices, connection pooling, kab queue karein

Jab aap MCP production mein use karte ho, teen cheezein matter karti hain jo development mein nahi dikhai.

**Transport choice.** Do transports hain, har ek ke trade-offs hain:

| Transport | Kahan kaam karta hai | Latency | Limitation |
|-----------|---------------------|---------|------------|
| stdio | Local, same machine | Bohot kam (no network) | Sirf local processes; ek agent = ek server instance |
| HTTP (Streamable) | Local ya remote | Network latency add hoti hai | Multiple agents ek server share kar sakte hain |

Development ke liye stdio almost hamesha sahi hai. Production mein, agar aapka MCP server alag machine par hai (managed service, container, ya serverless), toh HTTP use karna padega.

**Connection pooling.** `asyncpg.create_pool()` connection pooling provide karta hai — ek se zyada database queries ek saath chal sakti hain bina har baar naya connection banaye. MCP server mein pooling ka matlab hai ke multiple tool calls ek saath efficiently handle ho sakti hain. Ek important detail: **pool ko MCP server lifetime ke liye rakho**, har tool call par naya pool mat banao. Quick Win mein `_pool` global exactly yeh karta hai.

**Kab queue karein.** Agar aapka MCP server bohot zyada requests handle kar raha hai, do options hain:

1.  **Connection pool size barhao.** Default pool size usually 10 connections hai. Agar aapke paas 50 concurrent tool calls hain, toh pool size 50+ karo. Yeh immediate fix hai.
2.  **Queue add karo.** Agar database connections limited hain (managed Postgres ke limits), toh MCP server ke andar ek queue rakho jo requests ko ek ek karke process kare. Yeh zyada complex hai lekin database ko overload hone se bachata hai.

Zyada tar cases mein, pool size barhana sufficient hai. Queue sirf tab chahiye jab database connection limits aapko force karein.

:::note Quick check

Aapka MCP server stdio par chal raha hai aur aap 100 concurrent users serve karna chahte ho. Kya stdio sufficient hai? Jawab: **Nahi.** stdio ek subprocess hai — ek agent = ek server instance. 100 concurrent users ke liye, aapko HTTP transport chahiye taake multiple agents ek server share kar sakein, ya 100 alag server instances chalani padengi.

:::

### Decision 2: MCP server — customer-data MCP banao

Quick Win ka `notes_mcp.py` ek proof-of-concept tha. Ab real MCP server banao jo customer support operations expose kare:

```python
# src/chat_agent/mcp/customer_data.py
import json
import os
import asyncpg
from mcp.server.fastmcp import FastMCP
from pgvector.asyncpg import register_vector

mcp = FastMCP("customer-data")

_pool = None

async def get_pool():
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(
            os.environ["DATABASE_URL"],
            init=register_vector,  # pgvector registration!
        )
    return _pool

@mcp.tool()
async def lookup_customer(customer_id: str) -> dict:
    """Look up a customer by ID. Returns name, email, account_status, created_at."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        row = await conn.fetchrow(
            "SELECT id, name, email, account_status, created_at "
            "FROM customers WHERE id = $1",
            customer_id,
        )
        if row is None:
            return {"error": "Customer not found"}
        return {k: str(v) if not isinstance(v, str) else v for k, v in dict(row).items()}

@mcp.tool()
async def get_ticket(ticket_id: str) -> dict:
    """Get a support ticket by ID. Returns full ticket details including status and priority."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        row = await conn.fetchrow(
            "SELECT id, customer_id, subject, body, status, priority, created_at "
            "FROM tickets WHERE id = $1",
            ticket_id,
        )
        if row is None:
            return {"error": "Ticket not found"}
        return {k: str(v) if not isinstance(v, str) else v for k, v in dict(row).items()}

@mcp.tool()
async def search_similar_tickets(query: str, limit: int = 5) -> list[dict]:
    """Semantic search for similar resolved tickets. Returns top matches with resolution."""
    from openai import AsyncOpenAI
    client = AsyncOpenAI(api_key=os.environ["OPENAI_API_KEY"])

    # Embed the query
    response = await client.embeddings.create(
        model="text-embedding-3-small", input=[query]
    )
    query_vec = response.data[0].embedding

    pool = await get_pool()
    async with pool.acquire() as conn:
        rows = await conn.fetch(
            """SELECT d.id, d.title, d.body,
                      e.embedding <=> $1 AS distance
               FROM embeddings e
               JOIN documents d ON d.id = e.document_id
               WHERE e.document_id IS NOT NULL
               ORDER BY e.embedding <=> $1
               LIMIT $2""",
            query_vec, limit,
        )
        return [
            {"id": str(r["id"]), "title": r["title"],
             "body": r["body"][:500], "distance": round(r["distance"], 4)}
            for r in rows
        ]

@mcp.tool()
async def update_ticket_status(ticket_id: str, new_status: str) -> dict:
    """Update a ticket's status. Valid values: open, in_progress, resolved, closed."""
    valid_statuses = {"open", "in_progress", "resolved", "closed"}
    if new_status not in valid_statuses:
        return {"error": f"Invalid status. Must be one of: {valid_statuses}"}

    pool = await get_pool()
    async with pool.acquire() as conn:
        async with conn.transaction():
            result = await conn.execute(
                "UPDATE tickets SET status = $1 WHERE id = $2",
                new_status, ticket_id,
            )
            if result == "UPDATE 0":
                return {"error": "Ticket not found"}

            # Audit trail
            await conn.execute(
                """INSERT INTO audit_log (actor, action, target, payload)
                   VALUES ($1, $2, $3, $4::jsonb)""",
                "worker:customer-support", "ticket_status_updated", ticket_id,
                json.dumps({"new_status": new_status}),
            )

            return {"ticket_id": ticket_id, "status": new_status, "updated": True}

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

**Is MCP server ke baare mein key points:**

*   **Scoped tools.** Sirf safe operations: lookup, search, update status. Koi `DELETE`, koi `DROP`, koi schema changes.
*   **pgvector integration.** `search_similar_tickets` query-time embedding aur cosine distance use karta hai.
*   **Built-in audit trail.** `update_ticket_status` ek transaction mein ticket update aur audit row likhta hai.

### Decision 5: Document aur embedding pipeline — reference library

Ab reference library set karo. Knowledge base articles, policy documents, aur past resolved tickets ko `documents` table mein store karo aur embed karo:

```python
# src/chat_agent/embedding/pipeline.py
import os
from openai import AsyncOpenAI
import asyncpg
from pgvector.asyncpg import register_vector

EMBEDDING_MODEL = "text-embedding-3-small"

async def embed_and_store(
    pool: asyncpg.Pool,
    source: str,
    title: str,
    body: str,
    metadata: dict = None,
):
    """Embed a document and store it with its vector."""
    client = AsyncOpenAI(api_key=os.environ["OPENAI_API_KEY"])

    async with pool.acquire() as conn:
        async with conn.transaction():
            # Insert document
            doc_id = await conn.fetchval(
                """INSERT INTO documents (source, title, body, metadata)
                   VALUES ($1, $2, $3, $4::jsonb) RETURNING id""",
                source, title, body, json.dumps(metadata or {}),
            )

            # Embed (single chunk for short documents)
            response = await client.embeddings.create(
                model=EMBEDDING_MODEL, input=[body]
            )
            embedding = response.data[0].embedding

            # Register pgvector and store embedding
            await register_vector(conn)
            await conn.execute(
                """INSERT INTO embeddings
                   (document_id, chunk_text, chunk_index, embedding, model)
                   VALUES ($1, $2, $3, $4, $5)""",
                doc_id, body, 0, embedding, EMBEDDING_MODEL,
            )

            return doc_id
```

Resolved tickets, policy documents, aur knowledge base articles ko is function se embed karo. Woh phir `search_similar_tickets` MCP tool ke zariye searchable ho jaate hain.

### Decision 7: Audit trail integration

Audit trail already MCP server ke andar built-in hai (Decision 2 mein `update_ticket_status` audit row likhta hai). Ab agent-level audit add karo — har skill invocation aur har model call log karo:

```python
# cli.py — Decision 7: agent-level audit logging
import time

async def run_with_audit(pool, agent, message, conversation_id):
    """Run the agent with full audit logging."""
    started_at = time.monotonic()

    # Log user message
    await log_message(pool, conversation_id, "user", message)

    # Run agent
    result = await Runner.run(agent, message)

    # Log agent response
    await log_message(pool, conversation_id, "assistant", result.final_output)

    # Log the run as a capability invocation
    async with pool.acquire() as conn:
        await conn.execute(
            """INSERT INTO capability_invocations
               (conversation_id, capability, arguments, result, status, latency_ms)
               VALUES ($1, $2, $3::jsonb, $4::jsonb, $5, $6)""",
            conversation_id, "agent:run",
            json.dumps({"message": message[:500]}),
            json.dumps({"output_length": len(result.final_output)}),
            "ok",
            int((time.monotonic() - started_at) * 1000),
        )

    return result
```

Ab har action ka trace hai: user message, agent response, aur capability invocation — sab ek conversation_id se linked.

### Worker ki cost shape — operate karne mein asli kharcha kya hai

Ek Worker ko operate karne ka kharcha teen cheezon se aata hai:

| Kharcha ka source | Range | Notes |
|-------------------|-------|-------|
| LLM inference | $20–150/month | Model choice sab se bada lever. GPT-4o vs GPT-5.5 ka 5× farq ho sakta hai. |
| Database (Neon Postgres) | $0–25/month | Free tier 50 conversations/day ke liye sufficient. Paid tier scaling ke liye. |
| Embedding (OpenAI) | $0.02–1/month | 50K chunks embed karna = $0.30. Sirf naye documents ke liye. |
| **Total (single Worker)** | **$20–180/month** | Moderate use par $60–80 typical. |

50 Workers ki workforce ke liye:
*   Inference: $1K–7.5K/month (volume discounts milte hain)
*   Database: $25–200/month (shared Postgres, Neon paid tier)
*   Embeddings: $1–10/month
*   **Total: $3K–12K/month**

Key insight: inference hamesha dominant cost hai. Database aur embeddings negligible hain. Isliye model routing (saste model triage ke liye, mehenga model complex decisions ke liye) sab se bada cost lever hai.

### Swap guide — architecture invariant hai, products nahi

Yeh course specific products use karta hai, lekin architecture product-agnostic hai. Har cheez swap ho sakti hai:

| Component | Yeh course mein | Alternatives | Swap difficulty |

| Vector search | pgvector | Pinecone, Weaviate, Qdrant, Milvus | Medium — API alag hai, architecture same |
| MCP server | Custom stdio | Remote HTTP, managed MCP services | Easy — transport change, protocol same |

Architecture swap nahi hota: Skills + System of Record + MCP wire yeh teen moves hamesha rehte hain. Sirf products badalte hain.
